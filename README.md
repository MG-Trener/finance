# Семейная казна

**Семейная казна** — приватное веб-приложение для совместного учета доходов и расходов семьи из двух человек.

Продакшн: https://mg-trener.github.io/finance/

Интерфейс сохраняет морскую/пиратскую атмосферу в фоне, палитре и навигации, но рабочие кнопки намеренно сделаны обычными и понятными.

## Что умеет приложение

- общий семейный баланс и раздельная статистика мужа и жены;
- доходы и расходы с автоматической фактической датой и временем;
- категории, зависящие от типа операции;
- подкатегории, зависящие от категории;
- быстрый ввод операции с телефона и ПК;
- журнал операций с поиском, фильтрами и сортировкой;
- быстрое исправление суммы;
- полное редактирование операции;
- история изменений операции;
- мягкое удаление в корзину и восстановление;
- месячные бюджеты по категориям и предупреждение о приближении к лимиту;
- регулярные платежи и ближайшие обязательства;
- финансовые цели и накопления;
- годовая аналитика и сравнение периодов;
- сравнение участников семьи;
- экспорт CSV и Excel;
- звуковая обратная связь;
- адаптивная мобильная навигация;
- PWA: установка на домашний экран поддерживаемого телефона/ПК.

## Архитектура

Текущая версия — статическое клиентское приложение без отдельного backend-сервера приложения.

### Frontend

- HTML;
- CSS;
- Vanilla JavaScript;
- Supabase JavaScript Client;
- Chart.js — загружается только при открытии аналитики;
- SheetJS/XLSX — загружается только при экспорте Excel;
- Web Audio API для звуков интерфейса;
- Service Worker + Web App Manifest для PWA;
- GitHub Pages.

### Backend и база данных

Используется Supabase:

- PostgreSQL;
- Supabase Auth;
- Row Level Security;
- RPC для безопасного присоединения второго участника по приглашению;
- триггеры контроля целостности финансовых операций;
- журнал истории изменений операций.

## Основные сущности БД

- `profiles` — профили пользователей;
- `families` — семьи;
- `family_users` — связь пользователя с семьей;
- `people` — муж и жена как участники финансового учета;
- `categories` — категории доходов и расходов;
- `subcategories` — подкатегории;
- `transactions` — операции;
- `transaction_history` — история изменений операций;
- `budgets` — месячные лимиты;
- `recurring_payments` — регулярные платежи;
- `financial_goals` — финансовые цели;
- `goal_contributions` — пополнения/уменьшения целей;
- `family_invites` — одноразовые приглашения.

## Защита данных

Клиент работает с publishable key Supabase. Такой ключ может находиться в браузере; безопасность семейных данных обеспечивается не сокрытием ключа, а PostgreSQL RLS и проверками на стороне базы.

Основные правила:

- пользователь видит данные только семьи, членом которой он является;
- операции нельзя привязать к человеку из другой семьи;
- тип операции проверяется на соответствие категории;
- подкатегория должна принадлежать выбранной категории;
- `created_by` после создания операции не должен подменяться при редактировании;
- изменения фиксируются через `updated_by` и `updated_at`;
- удаление операции является мягким: используются `deleted_at` / `deleted_by`;
- история изменений хранится отдельно и доступна только членам соответствующей семьи;
- функции с повышенными правами не должны быть доступны роли `anon`.

После изменений схемы рекомендуется регулярно запускать Supabase Security Advisor и Performance Advisor.

Отдельная эксплуатационная настройка: в Supabase Auth рекомендуется включить **Leaked Password Protection**.

## Доступ второго участника

Приложение рассчитано на одну семью из двух аккаунтов.

Первый пользователь создает семейную базу. Второй подключается по одноразовой ссылке-приглашению. Клиентская форма регистрации показывается только при наличии приглашения, а фактическое присоединение выполняется серверной RPC-функцией с проверкой токена, срока действия, пользователя и лимита участников.

Даже если кто-то самостоятельно создаст аккаунт в Supabase Auth, это не дает ему доступа к чужой семейной базе: доступ определяется RLS.

## Мобильный интерфейс

Нижняя панель намеренно ограничена пятью пунктами:

- Обзор;
- Операции;
- Аналитика;
- Бюджеты;
- Ещё.

В «Ещё» находятся Цели, Регулярные, Категории, Доступ и, когда браузер поддерживает установку, действие установки PWA.

Мобильные `<select>` в форме операции заменены тематическим bottom sheet. Открытие происходит только по явному тапу — обычная вертикальная прокрутка через поле не должна раскрывать список.

## PWA

Файлы:

- `manifest.webmanifest`;
- `sw.js`;
- `src/js/core/pwa.js`;
- `assets/icon-192.png`;
- `assets/icon-512.png`;
- `assets/app-icon.svg`.

Service Worker обслуживается из корня `/finance/`, поэтому его scope покрывает приложение GitHub Pages.

## Локальный запуск

Нужен обычный HTTP-сервер — открытие через `file://` не рекомендуется, особенно для Service Worker.

```bash
python -m http.server 8000
```

Затем открыть `http://localhost:8000/`.

Для полноценной работы приложение должно иметь доступ к настроенному проекту Supabase.

## Развертывание

Продакшн работает через GitHub Pages из ветки `main`.

После commit/push GitHub Pages публикует новую версию. При крупных изменениях клиентских файлов версия query-параметров в `index.html` повышается, чтобы браузер и Service Worker не удерживали устаревший JS/CSS.

## Приоритеты дальнейшей разработки

- продолжать уменьшать исторический CSS-долг в `styles.css` / `hotfix.css`;
- перевести большие журналы с клиентского лимита на серверную пагинацию;
- добавить автоматические регрессионные тесты основных сценариев;
- при необходимости добавить резервный экспорт/импорт данных;
- рассмотреть push-уведомления для регулярных платежей после отдельного согласия пользователя.
